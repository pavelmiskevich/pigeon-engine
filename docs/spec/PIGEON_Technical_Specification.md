## 0. Назначение документа

Этот документ объединяет:

1. основную концепцию Pigeon, сформированную в текущем проекте;
2. архитектурные решения Desktop AI Pet 2.0, которые являются фундаментом питомца;
3. новые механики, специфичные именно для голубя;
4. отдельную архитектуру Browser Game;
5. инфраструктуру Online/Ecosystem, включая PostgreSQL, Redis и Kafka.

Документ является исходной технической спецификацией для дальнейшей реализации в C#/.NET и
подготовки задач на реализацию.

### 0.1 Что является главным

Pigeon не является двумя независимыми продуктами.

> Один голубь. Один Simulation/Core. Реальный Desktop как один из миров. Процедурный город как
> второй мир.

Одинаковые доменные механики должны по возможности переиспользоваться между мирами: личность,
потребности, настроение, память, решения, поведение, progression и события. Общими являются
**намерения и affordances** (§8.1, §32). Навигация, физика и анимация у каждого мира свои (§10).

### 0.2 Что не следует делать · *изм. v1.1*

- Не создавать на Desktop **невидимый** виртуальный город и другие скрытые симулируемые объекты.
- Не моделировать невидимые виртуальные машины, окна или автомобили, на которых голубь якобы сидит.
- Не имитировать данные, которые платформа не даёт (позиции окон, курсор): вместо этого
  понижается уровень опыта ([матрица](../platform/capability-matrix.md)).
- Не делать Jev realtime-контроллером.
- Не делать сеть обязательной для жизни Desktop-питомца.
- Не добавлять Redis/Kafka в Desktop только ради использования любимого стека.
- Не превращать Pigeon в обычного AI-assistant.
- Не давать AI прямой доступ к ОС.

**Уточнение ADR-0002.** *Видимые* объекты оверлея, которые создал пользователь или голубь
(крошки, помёт, перо), допустимы. Они существуют для пользователя так же, как сам голубь. Их
число и время жизни ограничены (§8.7).

## 1. Product Vision

Pigeon — живой цифровой голубь, который существует рядом с пользователем.

В Desktop Edition его физический мир — реальный рабочий стол пользователя: мониторы, области
экрана, окна, taskbar, курсор, приложения и доступные OS-события.

В Browser Edition его мир — полноценный процедурно генерируемый город с улицами, зданиями,
крышами, проводами, машинами, NPC, едой, гнёздами и другими объектами.

Питомец должен производить впечатление существа, которое живёт собственной жизнью:

- гуляет и летает;
- сидит на подходящих поверхностях;
- исследует окружение;
- скучает;
- хочет внимания;
- спит;
- играет;
- интересуется движущимися объектами;
- запоминает события;
- меняет настроение;
- развивает отношения с пользователем;
- совершает редкие и неожиданные поступки;
- иногда ведёт себя независимо от пользователя.

Главный UX-критерий:

> Пользователь должен чувствовать, что рядом действительно живёт характерный голубь, а не
> проигрывается набор анимаций.

Второй UX-критерий · *нов. v1.1*:

> Голубь никогда не мешает работать: не забирает фокус, не перехватывает клики мимо себя,
> не попадает в демонстрацию экрана и затихает, когда пользователь занят.

## 2. Product Modes

### 2.1 Desktop Pet

Целевые платформы: Windows 10/11, Linux, macOS. Порядок поддержки и уровни — в §2.3.

Desktop должен быть Local-First / Serverless-by-Default.

Без сети должны продолжать работать: мир, физика, анимации, перемещение, multi-monitor,
cursor interaction, personality, needs, mood, memory, relationship, progression, achievements,
life story, deterministic AI, Utility AI / FSM, настройки, developer mode, локальный event journal.

### 2.2 Browser Game

Browser Edition использует тот же Pigeon Engine, но другой World Adapter.

Мир: процедурный город, улицы, здания, крыши, балконы, провода, деревья, мусор, источники еды,
гнёзда, NPC, автомобили, другие голуби, погодные и временные события, опасности,
интерактивные объекты.

Browser Edition может быть online и multiplayer.

### 2.3 Платформы, уровни поддержки и деградация · *нов. v1.1*

Возможности платформ неравны: например, Wayland не отдаёт приложению позиции чужих окон и
глобальный курсор. Подробная матрица и механизмы — в
[capability-matrix.md](../platform/capability-matrix.md) (ADR-0011).

**Уровни Desktop-опыта** определяются во время работы по набору доступных возможностей:

| Уровень | Название | Суть |
|---------|----------|------|
| L3 | Full Desktop World | Насесты на окнах с учётом окклюзии, курсор на расстоянии, Application Awareness |
| L2 | Screen World | Поверхности экрана: work area, taskbar/Dock, края мониторов; без насестов на окнах |
| L1 | Window Mode («вольер») | Голубь живёт в обычном окне; вся симуляция сохраняется |
| L0 | Background | Без отрисовки; симуляция с редким тиком |

**Правило:** поведение, которому нужна отсутствующая возможность, не выбирается (оценка = 0).
Отсутствующие данные не имитируются. Уровень и отсутствующие возможности показываются
пользователю в настройках.

**Уровни поддержки платформ** **[Proposed]**:

| Tier | Платформа | Ожидаемый уровень | Когда |
|------|-----------|-------------------|-------|
| 1 | Windows 11, Windows 10 | L3 | MVP-1 |
| 2 | macOS, Linux X11 | L3 | MVP-2 |
| 3 | Wayland KDE / wlroots | L2 | MVP-2, best effort |
| 3 | Wayland GNOME | L1 (L2 — через расширение Shell, позже) | MVP-2, best effort |

Архитектура платформенно-независима с первого дня: `ICapabilityProbe` и платформенные адаптеры
закладываются в MVP-0, даже если реализация для Tier 2/3 приходит позже.

### 3.2 Правила зависимостей

```
Common ← Core ← AI ← Simulation
          ↑       ↑
   World.Abstractions
          ↑
   World.Desktop / World.City ← World.City.Generation
          ↑
   хосты: Desktop(+платформы) / Web.Client / Server
```

- Ядро (`Common`, `Core`, `AI`, `Simulation`, `World.Abstractions`, генератор) не ссылается на
  UI, ОС, сеть, БД и DI-контейнер. Проверяется `Pigeon.Architecture.Tests`.
- Ядро trim- и AOT-safe: без рефлексии по неизвестным типам и `Reflection.Emit`, сериализация
  через source generators. Это нужно для WASM (§4.3).
- `OperatingSystem.IsWindows()` и подобное допустимы только в платформенных проектах.

### 3.3 Контракт детерминизма · *нов. v1.1*

Детерминированы (ADR-0016):

1. **Симуляция ядра** при одинаковых seed, начальном состоянии, конфигурации, записанном
   потоке входных событий и **записанных решениях внешних провайдеров**.
2. **Генерация города** при одинаковых `WorldSeed` и `GeneratorVersion` — побитово, в любом
   рантайме (CoreCLR x64/arm64, .NET WASM).

Не детерминированы и не обязаны быть: отрисовка, тайминги ОС-событий, ответы Jev и LLM
(поэтому они записываются в журнал).

Правила:

- собственный ГПСЧ (PCG32 или xoshiro256**) с **именованными потоками** на подсистему, чтобы
  новый случайный вызов в одной подсистеме не сдвигал другие; `System.Random` в ядре запрещён;
- время — только через `IClock`; `DateTime.Now` в ядре запрещён;
- фиксированный шаг симуляции, отделённый от частоты кадров;
- генератор мира — на целочисленной или фиксированной арифметике, без `Math.Sin/Cos/Pow`;
- обход коллекций — в стабильном порядке, без зависимости от порядка `Dictionary`/`HashSet`.

## 4. Technology Stack · *изм. v1.1*

### 4.1 Core

- C#, .NET 10 (LTS)
- детерминированная симуляция по контракту §3.3
- dependency injection — только в хостах
- async API — для внешних провайдеров; симуляция внутри тика синхронна
- immutable/read-only снимки состояния для провайдеров, UI и Developer Mode

### 4.2 Desktop

- C#/.NET, платформенные адаптеры
- прозрачный always-on-top оверлей; **стек отрисовки выбирается в MVP-0** (S0.2, ADR-0021).
  Кандидаты: Avalonia 12 + нативный interop; тонкий нативный слой + SkiaSharp; SDL3/GLFW.
  Окно настроек может быть на Avalonia независимо от выбора для оверлея
- SQLite (единственное локальное хранилище; PostgreSQL на Desktop — нет, ADR-0019 **[Proposed]**)
- in-process доменные события
- опционально: Jev, Ollama, Cloud LLM

### 4.3 Browser · *изм. v1.1*

Рекомендация (ADR-0014 **[Proposed]**, подробно — [browser-runtime.md](../research/browser-runtime.md)):

- **ядро на .NET WebAssembly** (`wasmbrowser`, JSImport/JSExport, без Blazor-компонентов);
  те же сборки на клиенте и на сервере;
- **рендер на TypeScript**, основной кандидат — **Babylon.js** (WebGPU с откатом на WebGL2),
  за тонким слоем `RenderBridge`;
- ASP.NET Core, SignalR/WebSocket, PWA;
- PostgreSQL, Redis; Kafka — когда объём событий этого требует.

Окончательный выбор рендера — после прототипа B1 перед MVP-4. Ограничения на ядро (§3.2, §3.3)
действуют с MVP-1.

### 4.4 Дистрибуция и обновления · *нов. v1.1*

- Установщик и автообновление, кандидат — Velopack (решение в MVP-0, S0.9).
- Windows: подпись кода (иначе SmartScreen). macOS: Developer ID, hardened runtime,
  нотаризация, `LSUIElement`. Linux: AppImage и/или .deb; Flatpak — после оценки ограничений
  песочницы.
- Автозапуск — opt-in при первом запуске.
- Отчёты о падениях сохраняются локально; отправка — только по явному согласию.

### 4.5 Локализация · *нов. v1.1*

Все пользовательские строки — в ресурсах с первого дня. Языки MVP-1: русский и английский.

## 5. Core Domain

### 5.1 Pigeon · *изм. v1.1*

```
Pigeon
├── Identity            PetId, имя, дата рождения, seed, внешний вариант, версия схемы
├── Personality
├── Needs
├── Mood
├── Relationship
├── Memory
├── LifeStory
├── Progression
├── Inventory           только Browser World
├── Location            WorldId + PlaceKey + поза (sit/perch/fly/...)
├── CurrentIntent       намерение и план поведения (§8.1)
└── Statistics
```

Identity должна быть стабильной. Смена AI provider не создаёт нового питомца. Смена мира
(Desktop ↔ City) тоже не создаёт нового питомца (см. Q2).

### 5.2 Personality · *изм. v1.1*

Трейты — `0..100`, генерируются при рождении из seed (нормальное распределение вокруг 50,
опционально архетипы). Трейты не являются UI-параметрами: они влияют на Utility AI, реакции,
динамику настроения и контекст для Jev.

Четырнадцать трейтов v1.0 частично дублируют друг друга, а разницу между ними пользователь не
заметит. Настраивать их комбинации дорого. Состав **[Proposed]**:

| Трейт | Статус | Поглощает | Влияет на |
|-------|--------|-----------|-----------|
| Curiosity | базовый, MVP-1 | Exploration, Nosiness | Explore, Observe, реакция на новое |
| Playfulness | базовый, MVP-1 | — | Play, игры с курсором |
| Sociability | базовый, MVP-1 | Affection | рост Attention, SeekAttention |
| Boldness | базовый, MVP-1 | — | риск, реакция на резкие события |
| Calmness | базовый, MVP-1 | — | базовый arousal, скорость затухания эмоций |
| Independence | базовый, MVP-1 | Stubbornness | игнор пользователя, отказ от предложенных целей |
| Energy | базовый, MVP-1 | — | рост Fatigue, темп движения |
| Mischief | голубиный, MVP-2 | — | Mischief, бюджет сюрпризов |
| Greed | голубиный, MVP-2 | — | рост Hunger, реакция на еду |
| Territoriality | голубиный, MVP-2 | — | любимые места, защита насестов |

Примеры влияния: высокий Curiosity — чаще исследует новое; высокий Mischief — чаще выбирает
мелкие пакости; высокий Territoriality — защищает любимые места; высокий Boldness — меньше
избегает необычного; высокий Greed — сильнее реагирует на еду; высокий Sociability — чаще
ищет пользователя или других голубей.

Изменение трейтов со временем — открытый вопрос Q6. По умолчанию трейты фиксированы.

## 6. Needs · *изм. v1.1*

Needs изменяются локально и не принадлежат Jev. AI только принимает решения на основе состояния.

### 6.1 Модель

Каждая потребность — **срочность** `0..1` (больше = острее). В v1.0 полярность была разной:
Energy убывала, остальные росли. Теперь все потребности растут со временем и снижаются
удовлетворяющими намерениями.

Пороги (настраиваемые): `comfort < 0.3`, `want 0.3–0.7`, `urgent > 0.7`.

| Потребность | Поглощает (v1.0) | Растёт от | Снижают | С какого MVP |
|-------------|------------------|-----------|---------|-------------|
| Fatigue | Energy, Sleepiness | активности (полёт дороже ходьбы), циркадного множителя по локальному времени | Rest, Sleep | 1 |
| Boredom | Boredom, Curiosity (need), ExplorationNeed | отсутствия новых стимулов; Curiosity ускоряет | Explore, Play, Observe, Mischief | 1 |
| Attention | Attention, Affection | времени без взаимодействия с пользователем; Sociability ускоряет, Independence замедляет | взаимодействие, SeekAttention с ответом | 1 |
| Hunger | Hunger | времени и активности; Greed ускоряет | Eat | 2 |
| ToiletPressure | ToiletPressure | **после еды** (а не просто со временем) | Poop | 2 |
| Social | SocialNeed | отсутствия других голубей | общение с голубями | 4 (только City) |

**Stress** — не потребность, а производная величина настроения (§7).

### 6.2 Пример

```
Hungry + Curious + Bold
↓
Food detected
↓
High desire to investigate
```

### 6.3 Время отсутствия · *нов. v1.1*

Пока приложение закрыто или компьютер выключен, голубь «спал»:

- при запуске прошедшее время досчитывается **с ограничением**: не больше 8 часов эквивалента,
  и ни одна потребность от досчёта не поднимается выше `want` (0.7);
- последствий пренебрежения по умолчанию нет — голубь не болеет и не умирает (Q7);
- долгое отсутствие — событие `UserReturnedAfterLongAbsence`: радость или обида по личности и
  отношениям, запись в Life Story. Наказанием это не является.

## 7. Mood · *изм. v1.1*

Mood вычисляется локально. Jev может оценивать последствия действий, но не является источником mood.

**Модель:**

- `Valence` `-1..1` (неприятно ↔ приятно) и `Arousal` `0..1` (вялый ↔ возбуждённый);
- **базовая точка** задаётся личностью: Calmness снижает базовый arousal, Playfulness и
  Sociability сдвигают valence;
- **влияния**: срочные потребности тянут valence вниз и arousal вверх; события дают импульсы
  (поглаживание, испуг, еда); отношения сдвигают базовую valence;
- **затухание** к базовой точке по экспоненте (τ ≈ 10 минут, настраивается; Calmness ускоряет);
- **дискретные метки** выводятся из (valence, arousal) и доминирующей потребности: Content,
  Happy, Playful, Excited, Bored, Grumpy, Anxious, Startled, Sleepy. Метки используются для
  анимаций, UI и контекста провайдеров;
- **Stress** — скользящее среднее отрицательной valence при высоком arousal.

```
Mood = f(Personality baseline, Needs, Recent Events, Relationship, Environment)
```

## 8. Pigeon-Specific Behavior

### 8.1 Уровни поведения · *изм. v1.1*

В v1.0 в одном списке стояли движения (Walk, TakeOff), анимации (Flap, Groom) и цели (Explore,
SeekAttention). Теперь это три уровня (ADR-0013):

| Уровень | Что | Где живёт | Общий для миров? |
|---------|-----|-----------|------------------|
| **Intent** | *Что* голубь хочет: цель и её объект (affordance) | `Pigeon.AI` | ✅ |
| **Behavior** | *Как* в общих чертах: план из шагов `GoTo(affordance) → Action → Wait` | `Pigeon.AI` | ✅ |
| **Locomotion / Animation** | *Чем* именно: ходьба, взлёт, полёт, посадка, клипы | `Pigeon.World.*` | ❌ |

**Каталог намерений** (общий):
Rest, Sleep, Wander, Explore, Observe, Perch, SeekAttention, FollowTarget, Play, Eat, Drink,
Groom, Poop, Mischief, Hide, Flee, Relocate (другая территория или монитор),
LeaveOffscreen / Return (улететь за пределы экрана и вернуться; Desktop).

**Локомоция** (у каждого мира своя реализация):
Walk, Run, Hop, TakeOff, Fly, Glide, Land, Sit, Perch, FallRecover.

Мир публикует **affordances** — типизированные возможности (место для насеста, еда, точка
интереса, цель внимания, опасность, выход за экран). Ядро не знает координат: оно видит тип,
привлекательность, риск, стоимость пути и стабильный `PlaceKey` для памяти (§32).

### 8.2 Реакция на курсор

Курсор является реальным объектом Desktop World (при возможности C7; иначе — только когда курсор
над голубем).

Возможные реакции: наблюдать, подходить, убегать, следовать, пытаться поймать, раздражаться,
играть, игнорировать.

Реакция зависит от personality, mood, recent interaction и cooldown.

### 8.3 Насесты

Desktop (реальные поверхности, в зависимости от уровня L2/L3):

- видимые участки верхних кромок окон (L3, с учётом окклюзии — §11.4);
- taskbar / Dock / панели;
- нижняя кромка work area и края мониторов;
- другие platform-specific поверхности.

Browser City: крыши, провода, карнизы, вывески, балконы, фонари, деревья, другие подходящие
поверхности.

### 8.4 Словарь анимаций · *нов. v1.1*

Общий **семантический** набор клипов; каждый мир сопоставляет его своим ассетам (2D или 3D):

Idle, LookAround, Walk, Run, Hop, TakeOff, Fly, Glide, Land, Flap, Peck, Eat, Drink, Groom, Sit,
PerchBalance, Sleep, Wake, Coo, Startle, Puff (распушиться), Poop.

Параметры клипа: темп и поза (из arousal), направление. Формат ассетов Desktop решается в
MVP-0 (S0.8).

### 8.5 Poop / ToiletPressure

Poop — полноценное поведение, а не случайный таймер:

```
ToiletPressure → Threshold → Utility / Decision → Find suitable place → Move → Poop → Event
```

На Desktop визуальный эффект — объект оверлея (§8.7). Он не изменяет содержимое чужого
приложения. Пользователь может отключить или изменить это поведение.

### 8.6 Mischief

Примеры: сидеть на неожиданном окне; преследовать курсор; демонстративно игнорировать
пользователя; мешкать рядом с активным окном; устраивать короткие неожиданные события;
утащить или потрогать разрешённый игровой объект в Browser World.

В Desktop не допускается скрытая модификация пользовательских данных. Mischief подчиняется
бюджету сюрпризов (§23) и режиму тишины (§11.7).

### 8.7 Видимые объекты оверлея и еда на Desktop · *нов. v1.1*

На реальном рабочем столе нет еды, а ADR-0002 запрещает невидимые объекты. Поэтому:

- **крошки**: пользователь «бросает» их через меню голубя или трей. Это видимый объект
  оверлея, голубь подходит и клюёт;
- **перекус за экраном**: если Hunger срочная, а крошек нет, голубь может улететь за край
  экрана (`LeaveOffscreen`) и вернуться сытым. Это заодно выражает независимость;
- **помёт** и прочие следы: видимые объекты, исчезают через N минут или по клику; число
  ограничено (например, не больше 5);
- объекты оверлея не перехватывают клики, кроме явно интерактивных (крошки, помёт — по клику
  убираются).

## 9. Behavior Engine

### 9.1 Пайплайн

```
Decision (Intent) → Validate → Check State → Check Cooldown → Plan Behavior
  → Execute (World Adapter: локомоция, анимация) → Progress / Complete / Fail → Event
```

Результат выполнения возвращается в ядро событием: `Completed` или `Failed(reason)`, где
reason — `Unreachable`, `TargetGone`, `Interrupted`, `CapabilityLost` или `Timeout`. На неудачу
голубь реагирует (вспорхнул, огляделся) и выбирает новое намерение.

### 9.2 Utility AI · *нов. v1.1*

**Кандидаты.** Намерения из каталога × доступные affordances. Намерения без нужной
возможности или без affordance отбрасываются.

**Оценка.**

```
score(intent, target) = Π considerations_i(curve_i(x_i))   // каждая 0..1, с компенсацией за их число
                        × traitWeight(intent, personality)
                        × moodModifier(intent, mood)
                        × (1 + momentum, если это текущее намерение)
```

Примеры considerations: срочность соответствующей потребности, привлекательность и риск цели,
стоимость пути, новизна (из памяти), время суток, недавний кулдаун.

**Выбор.** Взвешенный случайный выбор из лучших K вариантов (K = 3), попавших в пределы δ от
лучшего (δ = 10 %). Это даёт характерность без полной предсказуемости.

**Устойчивость.** Минимальная длительность намерения и гистерезис переключения, чтобы голубь не
дёргался между двумя близкими вариантами; прерывание — только срочной потребностью или
значимым событием.

**Когда пересчитывать:** завершение или неудача намерения; значимое событие; переход
потребности через порог; периодически каждые 2–5 с.

**Данные.** Кривые, веса и кулдауны — в файле конфигурации (JSON), горячая перезагрузка в
Developer Mode. Настройка поведения — работа с данными, а не с кодом.

**Объяснимость.** Для каждого решения сохраняются 2–3 ведущих фактора как структурированная
причина (§36).

**Советники.** Jev и LLM не выбирают из всего каталога. Они получают уже отфильтрованный список
вариантов с локальными оценками и могут выбрать один из них или воздержаться (§17).

## 10. Physics · *изм. v1.1*

Physics — полностью локальный realtime-слой. **Физика, навигация и анимация у каждого мира
свои** (ADR-0013): экранная 2D-геометрия и 3D-город почти не имеют общего кода. Общими
остаются намерения, affordances, словарь анимаций и математические утилиты `Pigeon.Common`.

Jev не управляет: collision, movement per frame, animation frames, rendering, timing loops.

### 10.1 Desktop (`Pigeon.World.Desktop`)

- 2D-кинематика: ускорение, скорость, трение, гравитация при падении.
- Поверхности — граф отрезков: видимые кромки окон, taskbar, нижняя кромка work area, края мониторов.
- Полёт — параметрические траектории (баллистика, кривые Безье) с фазами TakeOff, Fly/Glide и Land.
- Прикрепление к поверхности: если окно-насест движется, голубь движется вместе с ним (§11.4).
- Единицы — логические пиксели: голубь одного размера на мониторах с разным DPI.
- Перелёт через зазор между мониторами или на несмежный монитор — «улетел за край и прилетел»:
  рисовать там, где нет монитора, нельзя.

### 10.2 City (`Pigeon.World.City`)

- 3D kinematic character controller для ходьбы, упрощённая модель полёта (подъёмная сила,
  сопротивление, планирование).
- Коллизии со зданиями (AABB или высотные карты кварталов), провода и карнизы — как
  поверхности-насесты.
- Навигационный граф: улицы, крыши, провода, деревья.
- Работает в 3D world coordinates; детерминизм генерации — по §3.3.

## 11. Desktop World

### 11.1 Основной принцип

Desktop World состоит только из объектов, которые действительно существуют на пользовательском
рабочем столе или доступны через OS metadata. Исключение — видимые объекты оверлея (§8.7).

Сущности: Monitor, ScreenArea, Window, Taskbar, Cursor, Application, DesktopArea,
Notification/Event metadata where safely available.

Не создавать скрытый виртуальный city simulation.

### 11.2 Окно-оверлей · *нов. v1.1*

Требования к окну, в котором рисуется голубь:

- прозрачное, с попиксельной альфой;
- click-through везде, кроме хитбокса голубя и интерактивных объектов оверлея;
- always-on-top, не забирает фокус, не видно в Alt-Tab, taskbar и Dock;
- по оверлею на монитор или один на всё виртуальное пространство — решается в MVP-0 (S0.2);
- отрисовка останавливается, когда голубь спит неподвижно или скрыт (§37);
- исключение из захвата экрана, где это возможно (C15, по умолчанию включено).

### 11.3 Monitor

Содержит: bounds, work area, resolution, DPI, scale, primary flag, topology, connection state,
стабильный идентификатор устройства (для `PlaceKey` и «любимого монитора»).

Поддерживать: подключение, отключение, изменение resolution, изменение DPI, sleep/wake,
RDP where supported.

### 11.4 Window и насесты на окнах · *изм. v1.1*

Безопасные metadata: application identity, title/metadata только при разрешении (§14),
position, size, state, visibility, active/inactive, z-order. По умолчанию не читать содержимое
окна.

**Окклюзия.** Оверлей рисуется поверх всего, поэтому голубь на перекрытом окне висел бы в
воздухе над чужим окном. Насестом может быть только **видимый участок** верхней кромки окна.
Видимые участки считаются по z-order: кромка минус проекции всех окон выше неё. Прототип и
бюджет (≤ 1 мс на 50 окон) — MVP-0, S0.4.

**Следование.** Голубь, сидящий на окне, прикреплён к нему и двигается вместе с окном (цель —
задержка ≤ 50 мс). Используются push-события там, где они есть (C10), иначе адаптивный опрос:
часто, пока голубь сидит на окне, редко в остальное время.

**Потеря насеста** — это событие, а не телепортация: окно закрыли, свернули, перекрыли или
развернули — голубь вспархивает, может «обидеться» или «испугаться» по личности. Это один из
самых выразительных моментов, его стоит беречь.

Не использовать как насест: окна оверлеев других программ, невидимые и cloaked окна, окна
других виртуальных столов, собственное окно настроек (если только это не забавно и не
разрешено отдельно).

### 11.5 Taskbar / Dock

Может выступать как поверхность, маршрут, зона наблюдения, место отдыха, источник событий.
Platform Adapter скрывает различия Windows/Linux/macOS.

### 11.6 Application Awareness

Питомец может учитывать: какое приложение активно, смену активного приложения, длительность
активности, запуск и закрытие приложения, изменение окна.

Это не означает чтение пользовательского содержимого. Для решений приложение сводится к
**категории** (browser, ide, office, media, game, messenger, other) по встроенному справочнику.
Имя приложения хранится только локально (§14).

### 11.7 Режим тишины · *нов. v1.1*

Голубь затихает — без mischief, poop, звуков и rare events; спит или тихо сидит у края — когда:

- активное приложение полноэкранное (игра, видео, презентация) — по умолчанию оверлей
  полностью скрывается и отрисовка останавливается. Это ещё и снижает риск конфликтов с
  античит-системами;
- включён системный «Не беспокоить» / Focus, если платформа это сообщает;
- пользователь включил «Тихо на 1 час» / «Скрыть до завтра» из меню голубя, трея или
  глобальной горячей клавишей (где доступна).

Выход из режима тишины плавный: голубь «просыпается», а не выпрыгивает.

### 11.8 Взаимодействие с пользователем · *нов. v1.1*

| Действие | Реакция |
|----------|---------|
| Клик по голубю | Погладить/ткнуть: реакция по настроению и отношениям, снижение Attention |
| Перетаскивание | Голубь «взят в руки»: хлопает крыльями, после отпускания — полёт или посадка |
| Правый клик по голубю | Меню: покормить, тихо на час, скрыть, имя, настройки |
| Иконка в трее / меню-баре | То же меню и выход; показ уровня опыта L0–L3 |
| Движение курсора рядом | Реакции §8.2 (при C7) |
| Крошки | §8.7 |

Звук (воркование, хлопки крыльев): тихий, отключается одним переключателем, молчит в режиме
тишины. Значение по умолчанию — Q12.

## 12. Multi-Monitor

Мониторы являются отдельными территориями.

Питомец может: исследовать новый монитор, иметь любимый монитор, перемещаться между
мониторами, иметь разные предпочтения по территориям, реагировать на подключение нового и
отключение текущего монитора.

Отключение монитора, на котором сидит голубь, — событие: голубь «падает» на соседний монитор
с испуганной анимацией, а не исчезает.

Life Story может фиксировать: First Multi-Monitor Transition, First Visit to Monitor, Favorite
Monitor Established.

## 14. Privacy · *изм. v1.1*

По умолчанию запрещены: screen capture, microphone, clipboard, arbitrary shell, browser
automation, arbitrary file access.

**Capability levels v1** (ADR-0020 **[Proposed]**):

| Уровень | Что даёт | По умолчанию |
|---------|----------|--------------|
| None | Голубь не знает ничего о рабочем столе, кроме мониторов (L1) | — |
| Metadata | Мониторы, геометрия окон, z-order, курсор, idle | **Вкл** |
| Application | Идентичность активного приложения | **Вкл** (только локально) |
| Window | Заголовки окон | Выкл |

Уровни Clipboard, Screen, Voice и ToolExecution из v1.0 **исключены из scope**. Голубю они не
нужны, а их появление противоречит «не превращать в AI-assistant». Возвращаются только
отдельным ADR.

Если capability требует разрешения: явное согласие, видимый статус, TTL where applicable,
revoke, audit log.

**Минимизация данных:**

- в журнал событий не пишутся заголовки окон и пути к файлам;
- во **внешние** провайдеры (Jev через OpenRouter, Cloud LLM) уходят только категории
  приложений и агрегаты, без имён приложений и заголовков. Для локальных провайдеров (Ollama)
  пользователь может разрешить больше;
- Developer Mode показывает **точный payload**, отправленный каждому провайдеру;
- «Очистить историю» удаляет журнал событий, но не питомца.

**Prompt injection.** Любой текст из ОС (заголовок окна, имя приложения) — недоверенные данные.
Ответ провайдера — строго структурированный, намерение выбирается только из переданного списка
вариантов (§17). Максимальный вред от инъекции — странный, но допустимый выбор поведения.

AI не получает прямой доступ к ОС.

## 15. AI Architecture

```
Pet State → Decision Context → Decision Router
  → Autonomous (Utility AI) ⇄ Advisors (Jev / LLM)
  → Intent → Behavior Engine → World Adapter
```

Jev — first-class decision layer, но не обязательный runtime network dependency.

## 16. Intelligence Modes · *изм. v1.1*

**Инвариант** (ADR-0015 **[Proposed]**): `AutonomousDecisionProvider` присутствует **всегда** и не
отключается. Остальные провайдеры — **советники** (`IDecisionAdvisor`) поверх него. Так
выполняется DoD «отключение Jev не ломает жизнь питомца» при любой конфигурации.

```
Decision layer
├── AutonomousDecisionProvider      всегда
└── Advisors (0..N, по приоритету)
    ├── JevDecisionAdvisor
    ├── OllamaDecisionAdvisor
    └── CloudLlmDecisionAdvisor

Cognition layer (не принимает решений; назначение — Q3)
├── None
├── OllamaProvider
└── CloudLlmProvider
```

Режимы v1.0 в новой модели:

| Режим v1.0 | Что это теперь |
|------------|----------------|
| Autonomous only | Без советников |
| Jev only | Jev-советник + Autonomous |
| Ollama only | Ollama-советник + Autonomous |
| Cloud LLM only | Cloud-советник + Autonomous |
| Jev + Autonomous fallback | Jev-советник + Autonomous — **default** |
| Jev + Ollama / Jev + Cloud / Jev + Ollama + Cloud | Цепочка советников по приоритету + Autonomous |

Jev — облачный провайдер (§17.1). Поэтому «default» означает рекомендуемую конфигурацию, а не
включённую из коробки. При первом запуске, без ключа и согласия, работает **Autonomous only**.
Jev включается после того, как пользователь ввёл ключ OpenRouter и явно согласился отправлять
обезличенный контекст (§14). Это прямо следует из §19: облачный провайдер не включается
незаметно.

## 17. Jev · *изм. v1.1*

### 17.1 Что такое Jev

Jev — модель структурированных решений от TypeSafe, доступная через OpenRouter
(`typesafe/jev-1.13`, алиас `~typesafe/jev-latest`). Это не чат-модель: она не генерирует текст
и не объясняет ответы, а возвращает **типизированное решение с вероятностями**. Поэтому она
хорошо подходит на роль «System One» голубя — быстрого выбора намерения.

| Параметр | Значение (на сентябрь 2026) |
|----------|-----------------------------|
| Endpoint | `POST https://openrouter.ai/api/alpha/decisions` (**alpha** — API может меняться) |
| Вход | `state` (строка или JSON-контекст) + `questions` (именованные вопросы) |
| Типы вопросов | `choice` — один вариант из набора; `noul` — да/нет; `score` — позиция на упорядоченной шкале |
| Ответ | `choice` + `confidence` + `probabilities` по каждому варианту; `noul` — вероятность «да»; `score` — взвешенная позиция |
| Контекст | 32 000 токенов (state + questions) |
| Цена | ~$0.04 за 1 млн входных токенов, выходные бесплатны; `usage.cost` в каждом ответе |
| Ограничения | Без объяснений и reasoning; вопросы одного запроса решаются параллельно и не видят ответов друг друга; задержка не документирована |

Jev — **удалённый** провайдер (`Locality = Remote`): к нему применяется privacy-фильтр для
внешних провайдеров (§14). Работает он только при наличии ключа OpenRouter и согласия
пользователя.

### 17.2 Сопоставление с контрактом советника

Один запрос к Jev на одно решение, в нём до трёх вопросов:

| Вопрос | Тип Jev | Откуда варианты | Что делаем с ответом |
|--------|---------|-----------------|----------------------|
| `intent` | `choice` | `DecisionRequest.Options`: ключ — индекс варианта, описание — короткий текст намерения и цели | Вероятности смешиваются с локальной оценкой (§17.4) |
| `remember` (при важном событии) | `score` | Шкала важности 0–4 | Предложение для Memory Service (§20) |
| `react` (при необычном событии) | `noul` | «Стоит ли реагировать» | Порог для rare event (§23) |

`state` собирается из `DecisionContext` после privacy-фильтра: личность, потребности, настроение
(метки), отношения, время суток, категории приложений, недавние события в виде кодов. Заголовков,
имён приложений и путей там нет.

Модель в запросе фиксируется на конкретной версии (`typesafe/jev-1.13`, не `-latest`). Снимок
модели из ответа (`model` с датой) пишется в журнал: без этого нельзя воспроизвести и сравнить
поведение.

### 17.3 Контракт

```csharp
public interface IDecisionAdvisor
{
    string Name { get; }
    AdvisorLocality Locality { get; }          // Local | Remote — для privacy-фильтра
    Task<AdvisorResult> AdviseAsync(
        DecisionRequest request,
        CancellationToken cancellationToken);
}

public sealed record DecisionRequest(
    DecisionCategory Category,
    long ContextVersion,
    DecisionContext Context,                   // снимок, прошедший privacy-фильтр
    IReadOnlyList<IntentOption> Options);      // только допустимые варианты с локальными оценками

public sealed record AdvisorResult(
    AdvisorVerdict Verdict,                    // Chose | Abstain
    int OptionIndex,                           // индекс в Options
    float Confidence,                          // 0..1
    IReadOnlyList<float>? Probabilities,       // по каждому варианту, если провайдер их даёт (Jev — даёт)
    ReasonCode Reason,
    string? ModelSnapshot,                     // например, снимок модели Jev из ответа
    long ContextVersion);
```

`IJevDecisionProvider` из v1.0 — это реализация `IDecisionAdvisor` для Jev.

Jev может решать: high-level behavior, social interaction, curiosity, exploration, user attention,
memory importance, rare events, personality expression.

Jev не делает: physics, collision, per-frame movement, animation frames, rendering, mouse
processing, window positioning, timing loops, database transactions, OS calls.

> Jev выбирает намерение; C# исполняет намерение.

### 17.4 Как ответ влияет на выбор

Вероятности Jev не заменяют Utility AI, а **смешиваются** с ним:

```
final(option) = utility(option) × (ε + p_jev(option))^w
```

`w` — вес советника (настройка, по умолчанию 1), `ε` — малая добавка, чтобы вариант с нулевой
вероятностью у Jev не исчезал совсем. Затем обычный выбор из лучших K (§9.2). Так Jev окрашивает
характер, а Utility гарантирует разумность. Вероятности около 0.5 означают неуверенность
модели, а не «средний» ответ.

Причина решения для пользователя (§36) собирается на нашей стороне, потому что Jev объяснений
не даёт: ведущие факторы Utility плюс «Источник: Jev, p = 0.62».

**Проверка ответа** перед применением:

1. ответ относится к текущему `ContextVersion` или моложе TTL (по умолчанию 10 с);
2. выбранный вариант по-прежнему допустим: цель существует, возможность не потеряна, кулдаун
   не наступил;
3. `Confidence ≥ threshold`;
4. иначе ответ отбрасывается с записью в журнал, решение остаётся за Autonomous.

Адаптер Jev изолирован в `Pigeon.AI.Jev` и покрыт контрактными тестами на записанных ответах:
API в статусе alpha, и его изменение не должно доходить до ядра.

Пока ответ не пришёл, голубь не замирает: он продолжает текущее намерение или выбирает
локально с пометкой «ожидается совет».

## 18. Jev Request Frequency

Jev не вызывается каждый frame/tick.

Триггеры: выбор следующего high-level behavior, необычное desktop event, возвращение
пользователя, длительное отсутствие, social interaction, exploration, curiosity, rare event,
memory importance.

Обычные realtime-операции локальны.

**Ограничения и стоимость** · *нов. v1.1*:

- частота по умолчанию — Adaptive: в среднем около 1 запроса в минуту при активном
  пользователе, всплески до 6 в минуту на значимых событиях, 0 во сне и в режиме тишины;
- не больше 1 одновременного запроса; таймаут 3 с (уточняется замером в MVP-0, S0.10);
- стоимость: при state около 1 500 токенов и ~$0.04 за 1 млн входных токенов запрос стоит
  ~$0.00006. Режим Adaptive при 8 часах в день — около $1 в месяц на голубя, режим High
  (6 в минуту постоянно) — около $5. Фактическая цена берётся из `usage.cost` и показывается в
  Developer Mode.

**Кто платит** **[Proposed]**: на Desktop — ключ OpenRouter пользователя (BYOK), хранится в
системном хранилище секретов (§33). В Online Edition запросы идут через сервер с ключом
сервера. Ключ сервера живёт только в секретах окружения и никогда не попадает ни в клиент, ни в
репозиторий.

## 20. Memory · *изм. v1.1*

Типы: Working, Episodic, Semantic, Relationship Memory.

- Воспоминания ссылаются на стабильные `PlaceKey` и `EntityKey` (например,
  `monitor:<device-id>`, `app-category:ide`, `taskbar:primary`), а не на координаты. Это
  позволяет «любимое место» пережить перезагрузку и смену раскладки.
- Новизна для Utility AI вычисляется из памяти: насколько знакомо место или объект.
- Важность считается локально; Jev может предложить `should_remember`, `importance`,
  `emotional_weight`. Запись выполняет Memory Service.
- Объём ограничен, работает кривая забывания; воспоминания Life Story не забываются.

Memory работает offline.

## 25. Browser Game

Цель первой игровой версии — дать пользователю наблюдать, как его голубь живёт в городе,
следовать за ним камерой (в том числе из-за спины) и влиять на его жизнь через мир.

**Модель управления** · *изм. v1.1*: **голубь летает сам** (решение владельца, Q10). Игрок не
ведёт голубя напрямую, а влияет косвенно:

- кормит и оставляет угощения в городе;
- «зовёт» голубя к месту — это предложение, которое голубь может проигнорировать по личности
  (Independence);
- обустраивает гнездо, выбирает, что сохранить из принесённого;
- управляет камерой: общий план, следование, вид из-за спины.

Это та же модель, что на Desktop: автономия + Utility AI + Jev, только мир другой. ADR-0010
соблюдается буквально — это голубь, а не аватар.

### 25.1 Перелётный голубь: один голубь, два мира · *нов. v1.1* **[Proposed]**

Ответ на Q2 (ADR-0022). Голубь **всегда находится ровно в одном мире**. Дом — Desktop, город —
место, куда он улетает.

**Как это выглядит:**

1. **Отлёт.** Голубь улетает за край экрана в город. Это может сделать пользователь («лети
   гулять») или сам голубь: ему скучно, пользователь долго отсутствует, у него высокие
   Curiosity и Independence. Отлёт — событие с анимацией, а не исчезновение.
2. **Жизнь в городе.** Если открыт Browser Edition, голубь живёт в городе вживую: пользователь
   смотрит, кормит, зовёт, встречает чужих голубей (multiplayer).
3. **Экспедиция.** Если в город никто не смотрит, его прогулка рассчитывается абстрактно и
   детерминированно из seed — без сервера и без физики. Итог — несколько событий, воспоминаний
   и находок. Так сохраняется local-first: перелёт работает и без сети.
4. **Возвращение.** Голубь прилетает на рабочий стол с находкой (пробка, перо, фантик) и новыми
   воспоминаниями. Life Story пополняется записями вида «встретил ворону на крыше вокзала».
   Настроение и отношения зависят от того, как прошла прогулка.
5. **Коллекция.** Находки хранятся в «гнезде» — панели коллекции. На рабочем столе можно
   выставить не больше 1–2 находок как объекты оверлея (§8.7).

**Почему это интереснее остальных вариантов:**

| Вариант | Оценка |
|---------|--------|
| Два разных голубя | Проще всего, но теряется главная идея «один голубь, два мира» |
| Один голубь одновременно в двух мирах | Ломает иллюзию существа (как он может быть в двух местах?) и даёт конфликты синхронизации |
| **Перелётный голубь** | Независимость (улетел сам), ожидание (что принесёт?), материал для Life Story, повод открыть город, социальный крючок — и технически самый простой вариант |

**Техническая модель:**

- **единственный писатель**: мир, где сейчас голубь, владеет его состоянием через
  аренду (residency lease). Перелёт — передача снимка `.pigeon` (§31) и журнала после него.
  Слияния состояний нет, поэтому нет и конфликтов;
- аренда города ограничена по времени. Если сессия в городе оборвалась, голубь «возвращается
  домой» с последним подтверждённым состоянием и ничего не теряет;
- в город уходит только состояние голубя. Воспоминания о рабочем столе переносятся в виде
  категорий, без имён приложений и заголовков (§14);
- экспедиция без Browser — чистая функция `(снимок, seed, длительность) → события`,
  проверяется детерминированными тестами.

**Развитие (MVP-6):** гости — голубь друга прилетает погостить на ваш рабочий стол; совместные
прогулки знакомых голубей в городе.

**Этапы:** экспедиция без Browser — MVP-2 (как часть «перекуса за экраном» и rare events);
живой перелёт в город — MVP-4; перелёт между устройствами через аккаунт — MVP-5/6.

Игровой цикл:

```
Explore → Find Food / Territory / Events → Interact → Progress → Unlock → Explore further
```

Потенциальные элементы: собственное гнездо, территории, другие голуби, коллекционирование,
progression, cosmetics, achievements, leaderboard, multiplayer.

## 26. Multiplayer · *изм. v1.1*

Multiplayer не меняет доменную модель одиночного голубя.

Server authoritative для: shared world state, interactions, economy, progression, matchmaking.

- **Свой голубь** симулируется на клиенте тем же кодом ядра; сервер проверяет влияния игрока

- **Город** генерируется на клиенте из seed; с сервера приходят только изменения относительно
  сгенерированного.

Client responsible for: presentation, local prediction, interpolation, input.

## 30. Event Architecture · *изм. v1.1*

Два разных вида событий, которые нельзя смешивать (ADR-0018 **[Proposed]**):

| | Доменные события | Интеграционные события |
|-|------------------|------------------------|
| Где | Внутри процесса, внутри тика симуляции | Между процессами и сервисами |
| Доставка | Синхронно, упорядоченно, детерминированно | Асинхронно, at-least-once |
| Контракт | Типы C#, меняются свободно | Версионируемая схема, обратная совместимость |
| Desktop | Диспетчер в `Pigeon.Simulation` | Локальный журнал (§31) |
| Online | То же | Transactional outbox → Kafka |

```csharp
public interface IDomainEventDispatcher
{

    IDisposable Subscribe<T>(IDomainEventHandler<T> handler) where T : IDomainEvent;
}

public interface IIntegrationEventPublisher
{
    ValueTask PublishAsync<T>(T @event, CancellationToken cancellationToken)
        where T : IIntegrationEvent;
}
```

`IEventBus` из v1.0 заменяется этими двумя интерфейсами. Реализации: `JournalEventPublisher`
(Desktop), `OutboxEventPublisher` → `KafkaRelay` (Online).

События доменные, а не привязанные к Kafka: PigeonSpawned, IntentStarted, IntentCompleted,

## 31. Persistence · *изм. v1.1*

Питомец живёт годами, поэтому совместимость сохранений — требование MVP-1, а не «потом»
(ADR-0017 **[Proposed]**).

**Модель:** журнал событий (append-only) + периодические снимки состояния (каждые N минут и
при выходе). Загрузка — последний снимок плюс события после него.

```csharp
public interface IPetStore
{
    ValueTask<PetSnapshot?> LoadAsync(PetId id, CancellationToken cancellationToken);
    ValueTask SaveAsync(PetSnapshot snapshot, CancellationToken cancellationToken);
}

public interface IEventJournal
{
    ValueTask AppendAsync(IReadOnlyList<JournalEntry> entries, CancellationToken cancellationToken);
    IAsyncEnumerable<JournalEntry> ReadAsync(PetId id, JournalQuery query, CancellationToken cancellationToken);
}

public interface ISchemaMigrator
{
    int CurrentVersion { get; }
    ValueTask MigrateAsync(CancellationToken cancellationToken);
}
```

Требования:

- SQLite в режиме WAL; запись — вне потока симуляции;
- версия схемы в каждой БД и в каждом снимке; миграции только вперёд; тесты миграций на
  фикстурах всех выпущенных версий;
- восстановление после аварийного завершения посреди записи;
- ротация резервных копий (ежедневно, хранить 7);
- журнал ограничен по размеру и возрасту (§37), Life Story и Memory не удаляются;
- **экспорт и импорт питомца** — один файл `.pigeon` (снимок + Life Story + Memory). Это основа
  для будущей синхронизации и «перелёта» между мирами (Q2).

Providers: `SqlitePetStore` (Desktop), `PostgreSqlPetStore` (Online). Смена provider не меняет
domain model.

```csharp
public interface IWorldAdapter

    WorldCapabilities Capabilities { get; }
    WorldSnapshot GetSnapshot();                                  // время суток, присутствие пользователя,
                                                                  // место и поза голубя, режим тишины, уровень L0–L3
    IReadOnlyList<Affordance> QueryAffordances(in AffordanceQuery query);
    ActionHandle Start(WorldAction action);                       // исполняется в тиках мира
    void Cancel(ActionHandle handle);                             // прогресс и результат — доменными событиями
}

public sealed record Affordance(
    AffordanceId Id,               // живёт, пока жив объект
    PlaceKey PlaceKey,             // стабильный ключ для памяти
    AffordanceKind Kind,           // PerchSpot, RestSpot, FoodSource, WaterSource, PointOfInterest,
                                   // AttentionTarget, Hazard, ToiletSpot, TerritoryZone, OffscreenExit
    float Attractiveness,          // 0..1 — оценка мира (высота, тепло, движение)
    float Risk,                    // 0..1
    TimeSpan TravelCost,           // оценка времени пути
    AffordanceTags Tags);
```

Новизна не входит в affordance: мир не знает, что голубь уже видел, — её вычисляет Memory.

Реализации: `DesktopWorldAdapter` (реальные объекты ОС через платформенные адаптеры, 2D) и
`CityWorldAdapter` (процедурный 3D-мир). Для тестов ядра — `FakeWorldAdapter` со списком
affordances без какой-либо геометрии.

## 33. Tool Security · *изм. v1.1*

В v1 у AI **нет инструментов**: советники выбирают только намерения из переданного списка
(§17). Architecture `Tool Request → Policy Engine → Allow / Deny / Ask User → Tool → OS`
проектируется отдельным ADR, когда появится первый реальный инструмент.

AI не получает прямого OS access. Все обращения к провайдерам логируются (§36).

**Credentials:** Windows Credential Manager, macOS Keychain, Linux Secret Service (если
keyring-демона нет — зашифрованный файл с явным предупреждением). API credentials не хранятся в
исходном коде, обычной JSON-конфигурации и логах.

## 34. Configuration

Настройки советников (для каждого): Enabled, Provider, Model (для Jev — фиксированная версия,
например `typesafe/jev-1.13`), Locality, Timeout, Retry, Max decisions/min, Max concurrent
decisions, Offline fallback, Confidence threshold, Advisor weight, Response TTL, Debug logging,
Privacy filter level.

Ключ API в конфигурации не хранится — только ссылка на запись в системном хранилище секретов (§33).

Decision categories: Behavior Selection, Social Interaction, Curiosity, Exploration, Memory
Importance, Event Interpretation, User Attention, Rare Events, Personality Expression.

Frequency: Off, Rare, Low, Normal, High, Adaptive.

Настройки поведения (кривые Utility AI, пороги, кулдауны, бюджет сюрпризов) — отдельный файл
данных, версионируемый вместе с кодом (§9.2).

## 35. Developer Mode · *изм. v1.1*

Базовый Developer Mode нужен уже в MVP-1: без него настройка Utility AI идёт вслепую.

Developer Mode позволяет:

- видеть current state, needs, mood, personality, current intent и план поведения;
- видеть оценки всех кандидатов Utility AI и ведущие факторы (§9.2);
- видеть decision context, provider, fallback и **точный payload**, отправленный провайдеру (§14);
- видеть уровень L0–L3 и таблицу возможностей;
- видеть event journal;
- ускорять время (×10, ×100) для проверки потребностей;
- симулировать события и запускать rare events;
- воспроизводить сессию из журнала (детерминированный replay, §3.3);
- воспроизводить Jev decisions, сравнивать Autonomous и Jev;
- делать health-check провайдеров;
- горячо перезагружать данные поведения.

Обязателен `SimulatedDecisionAdvisor` (в v1.0 — `SimulatedJevDecisionProvider`).

## 36. Observability

Минимум: structured logs, local event journal, provider latency, provider availability, decision
count, fallback count, отброшенные ответы советников (с причиной), behavior statistics, errors,
performance metrics.

Пользователь может понять, почему питомец принял важное решение, без раскрытия внутренних
chain-of-thought. Показывается структурированная причина:

```
Причина:  высокий уровень скуки
Решение:  исследовать другой монитор
Источник: Autonomous
```

## 37. Performance · *изм. v1.1*

Desktop Pet должен быть лёгким.

Требования: no per-frame AI requests; no mandatory network; no constant screen capture; bounded
memory; bounded event journal; adaptive simulation tick; reduced activity while system is idle;
render throttling when hidden or backgrounded. AI requests — event-driven.

**Целевые бюджеты** (эталонная машина фиксируется в MVP-0; значения подтверждаются или
исправляются по измерениям S0.2):

| Метрика | Цель |
|---------|------|
| CPU, голубь спит или сидит | ≤ 0.5 % среднего суммарного CPU |
| CPU, голубь в движении | ≤ 2 % |
| RAM (working set) | ≤ 150 МБ |
| Частота кадров в движении | 60 fps (30 fps на батарее) |
| Частота кадров в покое | ≤ 10 fps; 0, если сцена статична |
| Скрыт / режим тишины с полноэкранным приложением | 0 fps |
| Тик симуляции | 10 Гц (Desktop), адаптивно реже во сне и в L0 |
| Старт до первого кадра | ≤ 3 с |
| Журнал событий | ≤ 50 МБ, ротация по возрасту |
| Прирост памяти за 24 ч работы | ≤ 10 МБ (soak-тест) |

## 38. Testing · *изм. v1.1*

**Unit:** Personality, Needs, Mood, Utility scoring, Behavior transitions, Memory, Relationship,
Life Story, Physics (по мирам), procedural generation, окклюзия кромок окон.

**Integration:** Decision Router, advisors (Jev, Simulated), fallback, проверка устаревших
ответов, persistence и миграции, event dispatch и журнал, World Adapter с фейковыми
платформенными источниками для каждого уровня L0–L3.

**Architecture:** запрещённые зависимости ядра (§3.2).

**Determinism** (§3.3): при одинаковых Seed, Initial State, Events, Configuration и записанных
решениях провайдеров симуляция воспроизводима — в CI на Windows, Linux и macOS, x64 и arm64.
Генератор города даёт одинаковый хеш на CoreCLR и в .NET WASM (headless-браузер).

**Поведенческие «золотые» тесты:** симуляция суток ускоренным временем для нескольких
архетипов личности; распределение намерений попадает в ожидаемые диапазоны. Например, ленивый
голубь спит больше любопытного, а бюджет сюрпризов не превышается.

**Soak:** 24 часа работы без роста памяти сверх бюджета §37.

**Desktop** (автоматически через фейковые источники и вручную по сценариям): monitor changes,
window changes, окклюзия и потеря насеста, cursor, DPI и смешанный DPI, topology, sleep/wake,
RDP, fullscreen и режим тишины, unavailable permissions, понижение уровня на лету.

## 41. Definition of Done — Desktop · *изм. v1.1*

В v1.0 DoD включал элементы MVP-2 (насесты на окнах, rare events). Теперь он разделён.

### 41.1 MVP-1

- приложение запускается без интернета;
- голубь самостоятельно живёт; needs и mood изменяются самостоятельно;
- голубь физически перемещается по реальному Desktop уровня L2, в том числе между мониторами;
- реагирует на cursor и на взаимодействие пользователя;
- имеет personality;
- есть память, базовая life story, локальное сохранение с версией схемы;
- не забирает фокус, не мешает кликам, затихает при полноэкранном приложении;
- укладывается в бюджеты §37;
- отключение Jev не ломает жизнь питомца; Jev не управляет physics/frame loop;
- отсутствуют скрытые виртуальные объекты;
- не требует PostgreSQL/Redis/Kafka.

### 41.2 MVP-2 (полный Desktop DoD)

Всё из 41.1, плюс:

- может сидеть на реальных допустимых поверхностях окон (L3) с учётом окклюзии;
- понимает multi-monitor как территории;
- есть rare events в пределах бюджета сюрпризов;
- работает на Tier 1 и Tier 2 с ожидаемым уровнем, на Tier 3 — с честной деградацией.

## 42. Definition of Done — Browser

Browser MVP считается рабочим, если:

- город генерируется из seed, одинаково на клиенте и сервере;
- Pigeon Engine работает в CityWorldAdapter;
- голубь перемещается по 3D-миру;
- есть поверхности, еда, гнёзда, NPC и городские объекты;
- состояние сохраняется;
- сервер авторитетен для shared state;
- realtime transport работает;
- PostgreSQL используется для durable state;
- Redis используется только там, где нужен ephemeral/distributed state;
- Kafka подключается как event backbone на этапе, когда появляется соответствующий объём событий;
- бюджеты прототипа B1 выполнены.

## 45. Guiding Principle

> Мы не строим AI, который изображает голубя. Мы строим голубя, у которого AI помогает
> формировать характер и принимать решения.

В Desktop он живёт в реальном рабочем столе пользователя. В Browser он получает полноценный
процедурный город. Технически это один Pigeon Engine с двумя мирами.
